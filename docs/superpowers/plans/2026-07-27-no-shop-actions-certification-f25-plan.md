# No-shop actions certification F25 implementation plan

## Scope

Extend the exact F24 timing certification with five separately governed QXO
categorical comparisons:

1. prohibited actions;
2. action-level knowledge qualifiers;
3. exception prerequisites;
4. exception effects; and
5. the inline permission to inform persons of the no-shop restrictions.

F25 preserves 24 source occurrences and compares 23 unique action categories.
It certifies source, party, derivation, cohort, cache and Query identities. It
does not activate Canonical Query, change an active pointer, persist corpus
data, alter production or grant the frozen F6 source carriers release
authority.

F25 is an offline certification simulation, not an authoritative serving
consumer. Its local admission checks prove the five new records are internally
closed against the exact F25 manifest, but they do not add an exception to the
F22 central admission validator. F26 must register these admissions through
that central validator and use it for release assembly, import, request
compilation, projections and cache identity before any F25 record can become
release-eligible. The local F25 resolver and executor have no active or
production authority.

## Task 1: preserve frozen predecessors

1. Require the exact F24 bundle, manifest, registry and three timing carriers.
2. Require the exact F6 contract, admitted source, action mapping and exception
   source-binding carrier.
3. Prove the F6 and F24 inputs originate from the same immutable document and
   canonical text while allowing contract-versioned semantic context IDs to
   differ.
4. Recompute the source-context and canonical-text identities so re-signing
   altered source bytes cannot pass.
5. Do not modify F6 through F24.

## Task 2: certify atomic actions without losing occurrence identity

1. Retain all 24 ordered source occurrences, their exact evidence, source limb,
   party, ordinal, method links and claim revisions.
2. Derive the comparison set by exact action code, yielding 23 categories.
3. Preserve the two independently evidenced
   `FURNISH_NONPUBLIC_INFORMATION` occurrences inside one comparison category.
4. Carry the occurrence count and occurrence IDs in each category so the
   market statistic remains deal-weighted rather than occurrence-weighted.
5. Compare knowledge qualifiers separately. `KNOWINGLY` on facilitate and
   encourage must not be flattened into the action category.

## Task 3: certify exception prerequisites and effects

1. Retain all eight shared and two action-specific prerequisites.
2. Preserve the exact prerequisite set attached to each effect.
3. Certify the five express F6 effects with direct-source derivation.
4. Add two derived coverage effects for continuing discussions and
   negotiations. Each must:
   - preserve the direct source phrase “engage in or otherwise participate”;
   - identify the corresponding express participation effect;
   - use `INFERRED_BY_PARTICIPATION_SUBSUMPTION`;
   - carry a lawyer-visible ambiguity warning; and
   - remain distinguishable from an express permission in every output.
5. Certify the inline permission separately. Do not attach proposal,
   confidentiality, information-delivery or notice prerequisites to it.
6. Retain unresolved source residuals locally. A malformed or unresolved item
   may suppress only itself and its dependants, never sibling rows.

## Task 4: metric-scoped carriers and one bounded request

For each of the five metrics:

1. create one content-addressed admission with no wildcard authority;
2. create one source-backed categorical observation and one Query projection;
3. bind release, contract, metric, party, source and admission identities;
4. retain exact raw evidence alongside canonical comparison values; and
5. keep active-release, Query, pointer, write and production authority at
   `NONE`.

Create one combined no-shop market request containing the five exact metric
bindings. It must compile to one indexed, set-based SQL/RPC call. Its cache key
must include the predecessor release, F25 manifest, cohort refinements and the
sorted admission set. No per-action or per-effect database loop is permitted.

## Task 5: successor manifest and rendering isolation

Create one F25 manifest that:

1. binds the exact F24 bundle and manifest;
2. preserves all four timing admissions and adds exactly five categorical
   admissions;
3. requires exact set equality across the manifest, registry, carriers,
   combined request and Query records;
4. content-addresses every carrier partition;
5. remains ineligible for activation; and
6. distinguishes invalid, unresolved, non-comparable and feature-disabled
   states from generic `No market data`.

The manifest must carry
`F26_CENTRAL_ADMISSION_VALIDATOR_INTEGRATION_REQUIRED` until the F26 release
assembly proves all five admissions through the single F22 validator.

Rendering preparation must return every valid sibling even when one action,
qualifier, prerequisite, effect or permission member is malformed.

## Task 6: adversarial verification

Prove:

1. 24 occurrences become 23 deal-weighted categories without evidence loss;
2. duplicate furnishing occurrences do not double-weight the deal;
3. knowledge qualifiers remain tied to their exact action occurrences;
4. direct and inferred effects cannot substitute for one another;
5. the inferred continue effects carry a mandatory ambiguity warning;
6. prerequisite, effect, party, source, contract, release or admission
   substitution fails;
7. the inline permission cannot acquire exception prerequisites;
8. malformed members fail locally while valid siblings remain renderable;
9. forged re-signing cannot escape the exact source and F24 predecessor;
10. one page request has one corpus-independent database call and a cache hit
    has none; and
11. no route, flag, pointer, retry or production authority is introduced.

## Task 7: staging proof and shipment

1. Use only `deal-corpus-canonical-v2-staging`.
2. Validate the bundle locally before database work.
3. Insert all five certification records in one `jsonb_to_recordset` statement
   inside a short transaction with timeouts, advisory lock, RLS and revoked
   public access.
4. Roll back unconditionally and prove no table or pointer change remains.
5. Run focused and complete tests, production build, programme verification
   and the F25 phase allowlist.
6. Obtain independent Sol Ultra architecture and legal-semantic reviews.
7. Commit only F25 files, preserving
   `docs/codex-program/engine-build-map.md` untouched.
8. Push, merge after checks, deploy `deal-corpus`, smoke-test the disabled
   production APIs and continue directly into F26.
