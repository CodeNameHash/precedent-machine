### The routing rungs are not fact evidence

`routing_sonnet` and `routing_haiku` ran the routing and residual calls live and replayed the stored extraction loosely, so their fact columns are the stored answers read back. What they measure is routing agreement: Sonnet 5.5 at low effort routes 3.19 to REPRESENTATIONS alone (stored: MAE_DEFINITION, REPRESENTATIONS) and 5.17 to CAPITALISATION, GENERAL_COVENANTS (stored adds CONSIDERATION); Haiku 5.5 the same on 3.19. The stored routing is the broader one each time; whether the narrower routing loses facts needs a live extraction behind it, which this ladder did not run. Routing calls are 2 to 4% of a section's tokens ((181)), so this lever is small either way.

### Two defects for implementer E (work package E5)

1. `deterministic_routing` fails 5.17 with `GROUP_FAMILY: part1:g1`, and `routing_haiku` fails 5.17 with `GROUP_FAMILY: part3:g1`: when the routing differs from the stored run's, the part grouping no longer matches the stored calls and the loose replay throws instead of making a live call or reporting a miss. The rung should fall back to a live extraction for the part (and say so in the note), or the harness should report `REPLAY_MISS` with the part's family group.
2. The job table's cost column follows the CLI's reported cache split, so one rung's figure depends on what the previous rung sent minutes before; price every rung on the two fixed layouts above (every input token written, every input token read) beside the CLI's own figure.
