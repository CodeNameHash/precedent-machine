## The standard the stage is written against

Ben, 2026-08-09, correcting an earlier framing of mine that treated human review
as making correctness less urgent:

> **At thousands of agreements this doesn't work. The system needs to be
> fucking good! Humans will back fill edits but the system needs to do really
> well.**

Take this literally, because it changes what "done" means for every step.
Unattended correctness is the measure — not what a reviewer sees, and not
recovery volume. **A step that recovers claims but publishes some of them
wrongly is a worse outcome than the hold it replaced**, because a held row is
visibly incomplete and a wrong row is invisibly wrong.

The arithmetic behind Ben's point: at seven deals the corpus carries about **109
held rows and 385 unmapped candidates per agreement**. At a thousand agreements
that is **109,000 and 385,000**. No review queue absorbs that, and a queue that
large is not read — it is ignored, which is worse than not having one, because
it looks like a control.

## Step 2Y-0 is the one to understand before any other

It is Ben's ruling of 2026-08-09 and it changed the shape of the whole stage.

I proposed a threshold rule — publish only at or above the precision current
strict behaviour achieves. Ben's answer: **do not choose the cutoff, sweep it.**
Run each mechanism at several looseness levels, cross-reference each level
against independently deduced output, read the cutoff off the curve. That is
better, and it exposed that my rule depended on a baseline **nobody has ever
measured**: the 96-card blind sample measured whether *refusals* were correct,
not whether *publications* were.

Three things about it you need before you touch anything else:

1. **It changes how every other step is built.** You cannot sweep a ladder that
   does not exist, so **2Y-A through 2Y-J each ship rung-selectable and default
   to rung 0** — implementation lands inert, the sweep chooses the rung, then
   the rung is turned on. Two landings per step, and the acceptance evidence
   quoted in each step belongs to the second.
2. **The joint run gates, not the one-at-a-time sweeps.** The mechanisms
   interact: deferring to the model is only defensible once the context window
   made the evidence complete. Reporting the individual sweeps as the result is
   the exact shape of error this programme keeps making.
3. **The adjudicator is a model, and that can invalidate everything.** If it
   errs in the same direction as the extractor, the curve is confidently wrong.
   A **60–100 claim human-adjudicated anchor set from Ben** scores the
   adjudicators before their verdicts count. This is outstanding.

## Traps. These are not generic advice; each one cost this programme real time.

**This project's most expensive habit is forgetting what it has already built,
then rebuilding it or declaring it impossible.** `CLAUDE.md` lists the recent
examples. Before saying a thing does not exist: `grep -rn "name" lib/ scripts/
pages/ tests/`. Check `lib/` before `scripts/` — per-family work lives in the
library, and reading only the scripts gives the false impression it is absent.

**Read the code, not the comment.** A header claiming "this module only does X"
is a claim to test, never a fact to record. The 2026-08-09 re-audit found
**three DONE rows that were false**, one of which was a stale-header row that
was itself stale — it claimed a header had been corrected when it had not.

**A run receipt is not the model's output.** The receipt records what the
*shaper* produced. Red Hat's REPRESENTATIONS responses contain 69 limbs; the
receipt shows none, because the shaper discards them. Read `raw_response_text`.

**`review_queue` is the attempted set, not a reject pile.** Every attempted
claim, carrying `has_resolution` and `auto_pass`. The rate is
`resolved / review_queue`. Adding the two produced a reported 34.6% corpus rate
that should have been 52.8%.

**Never pipe test output into `head` or `tail`.** A pipeline returns the last
command's exit code and will report success on a failing suite. Redirect to a
file, `echo $?`, then grep the file. Use `CI=true`.

**Byte offsets are UTF-8; `indexOf` and `slice` are UTF-16.** Comparing one to
the other has produced three separate confident false findings, each looking
like a real defect. `lib/canonical-v2/canonical-bytes.js` converts. Do **not**
port `subclauses.js` to bytes — it has passing tests and four live V1 consumers;
convert at the boundary.

**A family returning zero can be correct.** Guaranty finds nothing on an
unfinanced deal because the agreement has no such provisions.

**`review-parity-check.js` exit 2 means nothing could be compared.** It is not
a pass.

**`pgrep -fc` matches the checking shell's own argv.** Count via `/proc` with
the checking shell excluded.

**Background agents die silently.** Verify by artefact — did the file grow, did
the branch move — never by notification.

**Replay costs zero model calls.** Prompt changes invalidate digests and
everything after is a live run at full cost: REPRESENTATIONS alone burned
2,734,334 output tokens across 172 calls for four deals. This is why 2Y-L exists
as a single deliberate bump rather than several.

## Why you should not trust this plan yet, and what to do first

Stage 2Y was written by one main loop (Opus) from the output of about ten
subagent passes, and reviewed adversarially once. `CLAUDE.md` is explicit that
what makes a review worth having is **independence** — the reviewer did not
write the thing and shares no context — and that **two models from one family
share training and tend to share blind spots**. Every diagnosis behind this plan
came from one vendor.

So, before implementing anything:

1. **Re-review the plan yourself**, against the register rather than against my
   summary of it. The register is the primary source; the plan is a reading of
   it.
2. **Run your own adversarial, from a different vendor** — GPT-5.6 Sol at high
   effort or Grok 4.5 at high effort, in a session that has not seen this
   conversation. `CLAUDE.md`'s routing table gives the equivalents. Ask it the
   structural question specifically: given these changes, is any fundamental
   change to the system's overall structure required or desirable? Fable was
   asked exactly that and **found a missing step** — so the question demonstrably
   pays, and one asking from one vendor is not enough for a claim this
   load-bearing. Give it `fable-review-stage-2y.md` **after** it has formed its
   own view, not before, or you will get agreement rather than a second opinion.
3. **Spot-check the load-bearing facts**, not all of them. The stage rests
   hardest on: the `sourceParagraphForCandidate` line-slice reading, the
   4,241 reconciliation, the 91-occurrence knowledge-standard finding with zero
   genuine conflicts, and the 707-of-713 identical-minting claim. If any of
   those is wrong, the step built on it is wrong.
4. **Then start with 2Y-0**, because every other step's acceptance gate is
   defined there, and an error there is invisible and propagates into all of
   them.

What would make me wrong in a way that matters: if the context-window mechanism
is smaller than measured, 2Y-A is over-weighted and the stage's ordering is
wrong. If the adjudicator cannot be calibrated against Ben's anchor set, 2Y-0
produces a curve that cannot be trusted and the whole stage loses its gate. Both
are checkable early and cheaply. Check them early.
