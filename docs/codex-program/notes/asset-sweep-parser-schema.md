## Detail: span accounting trio (span-residual.js, span-claims.js, resolve-source-span.js)

**span-residual.js** (`computeSectionResidual(sectionText, claimedSpans) -> { sectionChars, leafCount, residualChars, residualRatio, flagged, flagReason, drops }`). Takes a section's raw text, runs `segmentSubClauses` (subclauses.js) to get Part-1 leaves, and subtracts everything covered by `claimedSpans` (the union of every emitted item's claimed spans for that section, from span-claims.js). Ignores leaves < 200 chars and "benign chapeau" leaves (marker:null, matching a small set of transitional-phrase regexes, e.g. "the following", "subject to the foregoing"). Flags `EXTRACTION_INCOMPLETE` if residualRatio > 0.25 OR any single unclaimed leaf > 1500 chars. Header explicitly says this ONLY computes the flag — no enforcement, that's future work (rollout gates 2/3, not built). Code matches header exactly.

**span-claims.js** (`computeSpanClaims(sectionText, items) -> items with {claimedSpans, spanUnlocated, textSpan} attached`, non-mutating). For each item (any object with a `.text`/`.quote`/`.full_text` field), locates its text in the section via a 3-pass locator (exact indexOf -> whitespace-tolerant regex -> same regex on first 160 chars only, mirroring lib/verification.js's locateProvisionInSource pattern) and reports which Part-1 leaves it overlaps. `spanUnlocated: true` when text can't be found anywhere = hallucination surface. Also exports `attachSpanClaimsToProvisions(provisions, sectionTextByStartChar, opts)` — explicitly INERT unless called with `{spanClaims: true}`; when live it writes into `prov.features.spanClaims`, not top-level provision fields. Header calls out THREE separate span coordinate spaces in the repo (section-relative here; provision_cards.primary_quote_start/end relative to region_full_text; resolve-source-span.js's own marker-stripped-fulltext-relative space) and warns against conflating them — this is itself a useful map for anyone touching spans.

**resolve-source-span.js** — WP-5 module resolving a stored provision-card quote into offsets against the marker-STRIPPED deal full_text that SourceOverlay renders (full_text is laden with `[[REF]]`/`[[DEFINED]]` tags). `stripWithOffsetMap(rawText)` builds a bidirectional raw<->stripped index map. `resolveSourceSpan({fullText, quoteStart, quoteEnd, primaryQuote, regionFullText})` tries, in order: (1) explicit stored offsets IF `fullText.slice(quoteStart,quoteEnd) === primaryQuote` exactly, (2) exact/whitespace-normalized find of primaryQuote in stripped text, (3) same against the wider regionFullText, (4) `status: 'unresolved'` — never guesses. Header states store-cards.js's `primary_quote_start/end` are NOT absolute full_text offsets despite an earlier plan's claim — they're relative to the card's own `region_full_text` excerpt (verified against live data per the header) — a documented discrepancy worth carrying forward. `resolveCardSourceSpan(card, fullText)` is the convenience wrapper actually imported by `pages/review/[id].js` and `components/review-v2/SourceOverlay.jsx`.

**Coordinate space, ALL THREE**: every offset here is a plain JS string index (UTF-16 code unit), not a byte offset. None of the three files call any byte<->char conversion helper, and none needs to internally (they're self-consistent — computing and consuming their own offsets against the same string representation). The hazard is only at the boundary: if a caller elsewhere in canonical-V2 stores byte offsets (per CLAUDE.md's "byte offsets, not string indices" warning) and feeds them into `resolveSourceSpan`'s `quoteStart/quoteEnd` params expecting char-index semantics, offsets will silently be wrong on any non-ASCII deal text (curly quotes, em-dashes, section symbols are common in SEC filings). See byte-offset helper section below.

Tests: `tests/span-residual.test.js`, `tests/span-claims.test.js`, `tests/span-claims-wiring.test.js`, `tests/resolve-source-span.test.js` — run via `CI=true node --test <files>` (this repo uses node's built-in test runner, NOT jest — `npm test` confirms). Result: 40/40 pass, 0 fail.

Callers (real, not comment-only): `attribute-provision-section.js` imports `locateInSection` from span-claims.js live; `validate.js` imports `computeSectionResidual` live (Part 3 report path); `extract.js` imports `attachSpanClaimsToProvisions` live but gated inert-by-default; `scripts/span-residual-baseline.js` (the corpus-wide report-only runner, `reports/span-residual-baseline.json` exists — has been run) imports both `computeSpanClaims` and `computeSectionResidual`; `pages/review/[id].js` and `components/review-v2/SourceOverlay.jsx` import from resolve-source-span.js live, for the V1 review UI's "View in agreement" / SourceOverlay highlight feature.

**canonical-V2 usage**: `grep -rn` against `lib/canonical-v2/` and `scripts/canonical-v2*.mjs` finds exactly one hit, in `lib/canonical-v2/phase1-authority-boundary-inventory.js:122-124`, and it is a COMMENT ("Depends on ./span-claims so it cannot be PRODUCTION_PATH_PURE_ANALYSIS ... its own test and by scripts/span-residual-baseline.js"), not a require. **Canonical-V2 does not actually call any of these three modules.** This is exactly the pattern CLAUDE.md warns about — a mention that isn't a dependency — and it cuts the other way here: it means the residual-proof and span-claim machinery genuinely IS available to adopt into canonical-V2's extraction path, not already wired in under a name I'd miss.
