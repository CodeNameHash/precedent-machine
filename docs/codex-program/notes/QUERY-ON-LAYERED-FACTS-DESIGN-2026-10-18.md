# Query on layered facts: design note for Ben

Written 2026-10-18 by implementer C on the manager's brief (plan finding (163)), from the code at b77da65 and the stored runs on the preview branch. No code. Ben's words that set the scope, verbatim: "For query - we do need to build a query function etc but we should be thoughtful on how we do that once we have solid data we're happy with - add to the future planning (probably the first thing we build as it will drive the side bar etc)". Where a product decision is needed it is written as a question for Ben, numbered Q-A to Q-H at the end.

## 1. What a lawyer asks of a corpus

The questions below are Ben's own, from his 2026-09-12 review (`docs/codex-program/notes/BEN-NCS-REVIEW-COMMENTS-2026-09-09.md`) and his notes, each with the shape of the answer a query must give.

| The question, in Ben's words or his kind of words | What it asks the corpus for | The shape of the answer |
| --- | --- | --- |
| "what triggers the termination fee" (the `deal` skill's own example; the fee rows of his TopBuild and NCS reviews) | For one deal: the fee's payer, amount, every trigger and the termination right each trigger hangs off. Across deals: which deals share a trigger (a naked no-vote fee, a tail on a competing proposal) | One row per deal on the termination-fees table, the trigger column coded, the cited words behind each code |
| "which deals have a 48-hour notice" (the no-shop notice period) | Every deal whose notice period equals, or is under, a value | Deals filtered on a value cell (`nosol-noshop-notice`, column `period`) with the words behind the number |
| "show me every MAE carve-out for pandemics with a disproportionality carve-back" | Every deal whose MAE carve-out list contains a subject (pandemic) and whose carve-back applies to it | Deals filtered on a row of the MAE carve-out table (the carve-out subject) and a vocabulary cell (`disproportionateCarveback` = applies), the proviso's words beside each |
| "look across other deals ... and try and figure out the lines of separation" (on the MAE exclusion's three parts, 3.1) | The same limb of the same provision side by side across deals, so that the part that varies is visible | One column per deal, one row per limb, the limb's words in each cell |
| "you will need to track the reps and their bringdown and any exclusions/modifications per group of reps" (6.3) | Per deal, each representation's bring-down standard; across deals, which representations are brought down at which standard | The representations table's bringdown column (derived from the closing conditions) compared across deals |
| "come up with a category for each of them so we can compare them in the future" (the boilerplate interpretation rules) | Even the coverage-only provisions compared by category | A category axis per table, which the row labels and the sub-items already are |
| "are these items in Term canonical and being used across all deals? They need to be so they can be compared" (decision 31) | The same limb name in every deal | Q5: the canonical limb list per representation; a query on a limb is only possible once the names are canonical |
| "how tables were used to show similar data across variables ... just the headline conclusions" (the query mockups) | The old site's tables, one row per provision, coded conclusions, across deals | The table layout the provisions page already renders, with deals as a dimension |
| "we need to layer into the design the 'we have the backup' features of this new structure - i.e. show the evidence and all of the hard work behind the scenes" | Every coded answer opens to its words, clause and tree | The evidence sidebar on every query result, the same as on the provisions page |

Three kinds of question come out of this, and they decide the design:

1. **Find deals by a coded answer**: a vocabulary cell equals a code, a value cell is above or below a number, a row is present or absent. The answer is a list of deals with the cited words.
2. **Compare a provision across deals**: one table, deals as columns or as repeated row groups, the limbs aligned by their canonical names.
3. **Read one deal's provision with its evidence**: the provisions page as it is, reached from a query result.

## 2. What the layered facts and the conclusions cells already answer

The coded conclusions (`contracts/product/fact-conclusions.v1.json`, written by prompt bundle V9 and validated in `lib/product/fact-conclusions.js`) give every V9 fact a `table_key`, a `row_label`, an optional `row_detail` and `cells`, each cell one of a vocabulary `code`, a `value { canonical, unit }`, a `text` or a `present` boolean, with `component_refs` to the components that support it. The table shapes (`contracts/product/table-shapes.v3.json`, generated by the decision scripts) define the axes:

| Measure | Count |
| --- | --- |
| Sections | 30 |
| Tables | 49 |
| Vocabulary columns | 66 |
| Codes across the vocabularies | 449 |
| Value columns (numbers, periods, dates, percentages) | 34 |
| Fixed row lists (one row per provision, the legacy row vocabulary) | 46 tables |

So a query's filter axes exist today without new design work: a table, a row (the provision), a column, and a code or a number. The termination-fee question is `termination-fees-table` row by row with `trigger` (9 codes) and `amount`; the notice question is `nosol-noshop-notice` with `period`; the MAE question is `mae-carveouts-company` with its fixed row list (the carve-out subjects) and `disproportionateCarveback` (2 codes). The evidence is already attached: `lib/product/table-view.js` `attachWords` puts the cited words on every coded cell, and `applyColumnRules` and `pruneEmptyColumns` decide what the reader sees. Across agreements, the page work is `buildTableView` with facts from several runs and a deal dimension.

What the stored runs show about how far this reaches, read on the preview branch on 2026-10-18:

- Metsera generation 8 (READY) has 974 proposals, 961 VALID, with conclusions on every family that has a table; NCS generation 5 was at 734 proposals and still RUNNING; NCS generation 4 is bundle V8 and carries no conclusions at all. A query over conclusions therefore reaches V9 runs only.
- The representations tables' `row_detail` names (the limbs) are not yet canonical outside the nine seeded rows: 489 distinct names for 528 limb facts across two deals, 21 shared (plan finding (120)). A limb-level query (the 3.1 "lines of separation" question) waits on Q5.
- The two deals in hand are not comparable on everything: Metsera is a cash deal with a CVR, NCS a stock deal with an election; `consideration-election-options` and the CVR rows fill on one and read "Not a deal feature" on the other, which is itself the answer a query should give.

## 3. What the sidebar on a query result needs

The provisions page's `EvidenceSidebar` (`components/product/EvidenceSidebar.jsx`) takes a `fact` (headline, components with byte offsets, `section_reference`), the cited `componentIds`, the section's `sectionText` (the full section span from the run's spans, `lib/product/provisions-preview.js`), the `provenance` and checks, a `reviewItem` for the trail, and a `linkedDefinition`. Its three tabs are Detail (the words, the clause with the cited parts marked, the tree), Source text (the section with the fact's extent marked) and Comments. A query result that opens the same sidebar needs, per hit:

1. The fact itself with its component tree and byte offsets (the release summary carries `components`, `headline`, `coverage_only` and `section_reference`; `lib/product/review-state.js` `layeredFactExtras`).
2. The section text the offsets point into: today the provisions page reads it from the run's spans through the review read; a release has no spans of its own.
3. The conclusions cell that matched, with its `component_refs`, so the matched code opens on its words (the preview page gets this from the run's proposals; the release summary does not carry conclusions).
4. The agreement's identity for the header: the parties and the signing date, which no product table holds (`product_source_documents` has the retrieval URL and the hashes; the legacy `deals` table has acquirer and target with no link to a source document).
5. The review trail, which is per run (`product_review_sessions`), and the published decision, which is the release.

Ben's instruction that the query "will drive the side bar" reads, on this evidence, as: the sidebar's contract (fact, cited components, section text, provenance) is the unit a query returns, and the rail on the left lists the deals or the provisions the query matched, in the provisions page's design (finding Q3's rail and header).

## 4. What the published-facts read lacks for it

The read that exists (`pages/api/product/published-facts.js`, `ProductPhase3Store#listPublishedLayeredFacts`, plan item Q1) serves the current release head per source document and filters by family and subtype in memory. For the query above it lacks, in the order a build would meet them:

1. **Any release.** The preview branch has zero release heads and zero releases on 2026-10-18; the first comes with Phase 6's inactive release load and activation (implementer B's track). Until then the read answers an empty list, and a query built on it can only be exercised on draft runs.
2. **Conclusions in the release.** `compileReviewSummary` writes `components`, `headline`, `coverage_only` and `section_reference` onto each summary fact and nothing else; `conclusions` does not appear in `review-state.js`, `release-candidate.js` or `phase-3-store.js`. The coded cells, the whole filter surface, are in `product_proposals.payload` and `product_fact_conclusions` of the run, not in the release. Either the summary carries the cell rows (a change to `compileReviewSummary` and the publication validation in the database) or the read joins the release's run to `product_fact_conclusions` by `run_id` and `proposal_id` (a new read, the release pointer deciding which run).
3. **The section text.** A hit's Source tab needs the section's span; the release holds none. The read would join the release's run to `product_source_spans` (the full section span per node) or the summary would carry the section text per fact (several hundred kilobytes per agreement).
4. **Indexes.** `product_fact_conclusions` is keyed by `run_id, proposal_id` with no index on `table_key`, `row_label` or a cell's `column_id` and `code`; `cells` is a JSON column. At the corpus the product plans for (Ben's "four to five total distinct agreements" for the review, tens later) a scan is cheap; at hundreds of deals a cell filter wants either an expression index on the cell (a GIN index over `cells`) or a flattened table (`run_id, proposal_id, table_key, row_label, row_detail, column_id, code, canonical, unit`) written at publication. Not needed for the first step.
5. **Cell codes across runs.** A code is stable only while its vocabulary is: the table shapes are versioned (`table-shapes.v3.json`), a release records the run's `schema_version` and `prompt_bundle_version`, and a code renamed or split in a later shape version (as decision 34 did) leaves older releases coded in the old vocabulary. A query across releases needs either a code map per shape version or a re-publication of older releases under the current shape. The same holds for the row labels and, after Q5, the limb names.
6. **Agreement identity.** A query result is a list of deals; the product has no party names or dates for an agreement (section 3 above). The intake knows the SEC filing (`filing_accession`, `exhibit_filename`); the name of the deal needs either a field on `product_source_documents` set at intake from the filing index or a small table the lawyer fills.
7. **Filters on the read.** Family and subtype only, in memory, no paging; the query needs table, row, column, code and value comparisons, and a deal list.

## 5. Build order in three steps

The first step is a week's work for one implementer and needs nothing that is not already stored; the second and third wait on releases and on Ben's answers.

**Step 1, a week: the cell query over draft runs, on the provisions page's own reads.**
A read `GET /api/product/facts/query?table=<table_key>&row=<row_label>&column=<column_id>&code=<code>` (or `&min=`, `&max=` for a value column; `&present=true` for a row) over the runs the caller names (`&run=<id>` repeated, READY runs only, the latest generation per source document by default), answering `{ agreements: [{ run_id, source_document_id, agreement_label, hits: [{ fact_id, section_reference, row_label, row_detail, cell, words }] }] }`. It reads `product_proposals` (payload `conclusions` and `components`) and `product_source_closures` through the Phase 2 store, the way `lib/product/provisions-preview.js` does, so held and rejected facts stay out and the lawyer's edits apply. A page `pages/query/provisions.js` extended with the table, row, column and code selects (the options from `table-shapes.v3.json`, as the family and subtype selects come from `legal-schema.v2.json` today), the results as one `PublishedSummary` table per agreement with only the matching rows, and the existing `EvidenceSidebar` behind each cell with the section text from the run's spans. Tests: a fixture of two runs' proposals and the three questions of section 1 as assertions. This answers "which deals have a 48-hour notice" and "every MAE carve-out for pandemics with a carve-back" on Metsera and NCS the day it lands, on drafts, marked as drafts.

**Step 2, after the first release activates: the same query on releases.**
Move the read to the release pointer: the summary carries the conclusions cells (or the read joins the release's run's `product_fact_conclusions`), the section text comes from the run's spans by `run_id`, and the page marks each agreement as released with its date. Add the agreement's name (Q-F below). This is where the published-facts read of Q1 either grows into the query read or is retired in its favour.

**Step 3, once four or five deals are released and Q5 is decided: compare and the rail.**
A compare view: one provision's table across the chosen deals, the limbs aligned by canonical name, the varying cell highlighted; the rail lists the deals; the sidebar opens on any cell. A code map per shape version so older releases answer in the current vocabulary. The flattened cell table or the GIN index when the corpus needs it. This is the point at which legacy Compare's job is done by the product and the legacy code can go (Q4: it stays unrouted until then).

## 6. Questions for Ben

- **Q-A.** Should the first step run on draft runs (READY, latest generation per agreement, marked as drafts), so the query exists before the first release, or wait for releases and run on published facts only? The note assumes drafts first, marked.
- **Q-B.** Is the filter a form (table, row, column, code or number, deals), or a sentence the model interprets into that form, as legacy Query's interpret did? The note assumes the form first; a sentence can be mapped onto the same form later.
- **Q-C.** Does a query result show the matching rows only, or the whole provision table of each deal with the matching cell marked?
- **Q-D.** For the compare view, deals as columns (one row per limb, as your 3.1 comment reads) or deals as repeated row groups (the provisions page's tables stacked)?
- **Q-E.** Should the conclusions cells be published into the release summary, so a release is self-contained, or read from the run the release points at?
- **Q-F.** The deal's name: set at intake from the SEC filing index (target and acquirer from the cover page), or typed by you at publication?
- **Q-G.** When a vocabulary changes (a code split or renamed in a later table-shapes version), do older releases re-publish under the new shape, or answer through a code map?
- **Q-H.** Are held and rejected facts ever to be queryable (a "what did the extractor hold on this deal" view for you), or does a query see accepted facts only?
