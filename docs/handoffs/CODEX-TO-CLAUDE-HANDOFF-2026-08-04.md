## 46. Excerpt-identity audit under ruling 6, 2026-08-05

Full-repository audit against Ben's programme-wide rule that `excerpt_id` is not
a unique card identity. 837 hits triaged across roughly 80 files, plus the SQL
schema and the import graph.

### The coupling that makes this dangerous

Two findings are directly coupled, and this is the single most important thing
in the audit:

1. `supabase/schema-04-provision-card-canonical.sql:125-126` creates
   `UNIQUE INDEX provision_cards_excerpt_unique ON public.provision_cards(excerpt_id)`,
   a **bare** unique index on the live table, with no deal, provision,
   occurrence or revision component.
2. `lib/queries/claims-adapter.js` `groupClaimsByExcerpt` keys a Map purely on
   `claim.excerpt_id`, and `lib/queries/review-deal.js` reads it as
   `claimsByExcerpt.get(row.excerpt_id)`. **This runs on every served review
   page today**, with no gate and no dark stamp.

The DB constraint is currently the only thing preventing the live silent
corruption in (2). If two cards in one deal ever shared an `excerpt_id`, both
would receive the same merged claims array and card A would render card B's
features, with no error. Fixing either one alone makes the other the live
failure point. They must be reasoned about together.

Neither fires today, because legacy `excerpt_id` is minted as
`dealId:sectionPath:spanHash:index` and so happens to be 1:1 with a card. The
genuine canonical-v2 excerpt id is `contentId(EXCERPT_DOMAIN, {quote, start,
end})`, a pure function of text and offsets with no deal or provision
component. That is precisely the value type that legitimately repeats.

### Findings

| Severity | Location | Composition | Fires today |
| --- | --- | --- | --- |
| VIOLATION | `schema-04-provision-card-canonical.sql:125` | bare `excerpt_id` unique index | No, latent |
| VIOLATION, live path | `claims-adapter.js` `groupClaimsByExcerpt` | `excerpt_id` alone | No, blocked by the index |
| AT_RISK, live | `row-market-stats/observations.js`, `source.js` | `deal_id\|excerpt_id` | No |
| AT_RISK, live | `corpus-stats-core.js`, `corpus-duration.js` | `deal_id\|excerpt_id` | No |

| VIOLATION | `general-covenants-dark-bridge.js` | same pattern | No, gated |
| AT_RISK | `representations-dark-bridge.js` | synthetic `excerpt_id` still reserved | No, gated |
| SAFE | `no-other-reps-fraud-dark-bridge.js` | `provision_instance_id`; excerpt is data only | n/a |

`no-other-reps-fraud-dark-bridge.js` is the exemplar. Its header states the
rule almost verbatim and its merge deliberately does not reserve `excerpt_id`.
The other three are being brought to that standard.

The canonical-v2 core model was never the problem:
`canonical-writer.js`'s `OBJECT_ID_FIELDS` already uses `claim_revision_id`,
`provision_instance_id` and `provision_component_id` correctly, scoping
`excerpt_id` only to the excerpts table itself. Every violation is in the dark
bridge translation layer that flattens that correct model back into the legacy
card shape.

### A real cross-family bug this exposes

`mergeCanonicalV2CardsIntoReviewDeal` reserves `excerpt_id` across the whole
`reviewDeal` before looking at its own incoming cards. Because the No Other
Reps bridge correctly puts two sibling cards on one excerpt, merging its output
first and then any other bridge's output into the same reviewDeal throws
`ID_COLLISION`. **Chaining two bridges into one review deal is impossible
today.** That directly blocks ruling 3's "Review preview for all four areas
together", so it must be fixed before item 17.

### What is being done, and what is NOT

In flight: the three bridges are being corrected to bind identity on
`provision_instance_id`, with a cross-family merge regression; and the live
paths are being rekeyed on `deal_id` + `provision_instance_id` + `excerpt_id`
under a hard requirement that the change is a provable no-op on today's data.

**Not done, and needs Ben:** the DB unique index is production schema. Changing
it is a production data change and remains prohibited. It is recorded here as a
migration-rehearsal item only. The remediation, when authorised, is to drop
`provision_cards_excerpt_unique` in favour of the existing
`provision_cards_provision_instance_unique`, or to make it composite as
`UNIQUE(deal_id, provision_instance_id, excerpt_id)`. Until then, note that this
index will hard-block any future promotion path that writes canonical-v2 cards
into `public.provision_cards`, because such cards can legitimately share an
excerpt and the current upsert conflict target does not cover this index.

### Lower-severity note

`canonical_v2_staging.excerpts` uses `excerpt_id` as its primary key, which is
correct in principle since an excerpt's own identity is its content-addressed
span. Two deals sharing byte-identical boilerplate at identical offsets would
collide, but the writer raises a hard exception rather than merging silently,
so it degrades to an ingest failure a human resolves, not corruption.

## 47. Ruling 5 implemented: transitive serving-path analysis, 2026-08-05

The strict locator rule is implemented with a **real AST parser**, not regex:
`acorn` via `next/dist/compiled/acorn`, with `sucrase` lowering JSX. Both are
required lazily inside try/catch, so a missing parser fails the proof closed
rather than crashing the register. All 948 product files under `pages/`, `lib/`
and `components/` parse, including all 59 `.jsx`, in under a second. Zero
fail-closed exposure from parsing.

### The rule

A surface reads visible only on a complete path: served entry point →
transitive imports → proving consumer → exact adapter import → **intra-module
call graph → the exact `source_locator`**. `executedAdapterExportNames` returns
which exports the consumer actually executes; those become roots of a
reachability closure over the adapter's module-level call graph, together with
top-level code, which genuinely runs on import.

Export manifests (`export { … }`, `module.exports = { … }`,
`Object.freeze({ … })`) are excluded from the roots. Without that the rule
would be hollow, because every export would be trivially reachable from itself.
Locals declared inside a function are subtracted from its reference set, so
shadowing breaks an edge instead of inventing one.

Three discriminated locator rules: `FUNCTION_CALL_PATH`,
`MODULE_BINDING_PATH`, and `NON_FUNCTION_EVALUATION_SITE`. Everything else is
`UNPROVEN`: unparseable module, duplicated module-level binding, unresolved
re-export, unreachable locator.

### Effect on the inventory: none

104 blockers = 73 / 27 / 3 / 1, 6 review holds. Every pin held untouched. Only
three rows in the register have consumer proof at all and can therefore reach
the new gate:

| Row | Locator | Result |
| --- | --- | --- |
| `proxy-render-derived-deadlines` | `parseDeadlineText` | proves, `FUNCTION_CALL_PATH` |
| `termination-fee-render-derived-values` | `percentage_of_equity` | proves, `NON_FUNCTION_EVALUATION_SITE` |
| `termination-fee-query-derived-values` | `feePctOfDealValue` | does not prove; still reports the more specific `DERIVED_INTEGRATED_NOT_SERVED` under ruling 4 |

The motivating case proves genuinely transitively. The test asserts that the
consumer executes `deriveSecMeetingSummary` and **not** `parseDeadlineText`;
the proof arrives via `deriveSecMeetingSummary → normaliseDeadline →
parseDeadlineText`.

### Judgement call on non-function locators, resolved

The implementation brief listed `percentage_of_equity` under "must not prove".
**That brief was wrong, and the implementer was right to push back.** Verified
directly: `lib/termf.js:268` reads `ctf.percentage_of_equity` inside
`buildTerminationFees`; `termination-fees.config.js` imports it at line 2 and
calls it at line 214; both `pages/review-v1/[id].js` and
`components/review-v2/sectionList.js` import that config. The value is
genuinely evaluated on a served path and genuinely rendered.

Demoting it would have been an over-fence, which is exactly what ruling 5
forbids: "Do not demote a row merely because direct-import analysis is too
shallow." The adopted rule stands: a non-function locator must be **evaluated**
on a reachable path, present inside the body of a reachable function. Being
defined is not being served. A key that exists only in a top-level literal, in
dead code, or in a comment does not prove, which is why `feePctOfDealValue`
correctly fails.

Taking the harder line instead would demote `termination-fee-render-derived-values`
and move the count to 105. It is one branch in `locatorServingProof` if Ben
ever wants it, but it would misreport a value the product really shows.

### The gate is load-bearing, and proved so

### Forward finding: 19 rows have unprovable locators

Of the 73 `NATIVE_UNVERIFIED` rows, **19 have locators that are neither a

## 48. ADR-001: flattening is scaffolding, decided 2026-08-05

`docs/codex-program/ADR-001-dark-bridge-flattening-is-scaffolding.md`.

Ben accepted the position that flattening Canonical V2 output into the legacy
card shape is a preview and equivalence scaffold, never a serving path and
never a persistence path. The binding constraints:

1. Flattened cards must never be written to `public.provision_cards`, `claims`
   or any persistent store. No promotion, import, backfill or migration.
2. Native serving consumes V2 projections directly, not bridged cards.
3. Do not extend flattening beyond the four existing areas. A fifth bridge
   needs a new decision.
4. Bridge verification logic may be reused by a native path. It is the shape
   conversion that is scaffolding, not the guards.

Removal condition, testable rather than a matter of judgement: a bridge is
deleted outright, not left dormant behind a disabled gate, once every parity
surface for its area reports `NATIVE_VISIBLE` through a served consumer
importing the V2 projection directly under the strict locator rule.

Two consequences worth carrying forward:

- The parity register already enforces most of this mechanically. A bridge is
  unreachable from any served route, so it can never clear a blocker. What is
  **not** enforced is constraint 1: nothing in code stops someone persisting
  bridged cards except a DB index that exists for unrelated reasons and that
  the excerpt remediation may legitimately want to change. Anyone altering
  `provision_cards_excerpt_unique` must satisfy constraint 1 by other explicit
  means first.
- The ruling-1 preview lane depends on bridged cards, so it is scaffold-shaped
  too and inherits the same removal condition. It is not the eventual native
  Review surface.

The excerpt-identity remediation remains required regardless, because the live
read paths in `claims-adapter.js`, `row-market-stats` and the corpus-stats
helpers are real product code, not scaffolding, and their keying is wrong.

## 49. Data source for the Review preview route, item 17

A decision that has to be settled before the route is wired, recorded with its
reasoning because it rests on an interpretation of Ben's activation order.

The preview lane needs dark cards to render. There are only two honest sources:

1. **Fixtures**, the same ones the four bridge suites already consume. Safe,
   deterministic, no extraction, no database. Proves the rendering and merge

2. **Canonical V2 staging**, via `getCanonicalV2ServingClient()`, which returns

behaviour be activated and proved now, and leave source authenticity to the
step that exists for it.

This also keeps the honest-state requirement intact. A fixture-fed lane is

it can be mistaken for proof that a real source was admitted.

Note also that running extraction or model replay against live sources was
never lifted. The 2026-08-05 authorisation covers building and activating
routes on local and Vercel preview; it does not authorise extraction. Fixtures
respect that boundary; a pipeline run would not.

If Ben wants real staging data in the preview earlier, that is a one-line
change of source plus the item-18 boundary work, and it needs his word first.

## 51. The 19 unprovable locators, computed and corrected, 2026-08-05

### The important correction: zero of the 19 can be fixed by re-pointing a locator

Section 47 implied some rows might need only a locator correction. **That was

Every live caller hardcodes `included_field_groups: ['primary', 'qualifiers']`:

the register question and worth its own investigation.

`dno-query-compare-fields` and `employee-query-compare-fields` carry a

### `appraisal-governed-review` is the worst-placed of the 19

Its siblings `TAX_TREATMENT_PROTECTION_COVENANT` and

branch in `validateAttributes`, unreached today but a real token, so they are
wiring gaps. `APPRAISAL_SETTLEMENT_CONSENT` has no candidate evaluation site
anywhere, even in principle, without adding one. Additionally the module stamps
every record `VALIDATED_NOT_SERVED`, which the dark-authority fence actively
rejects from `deal-compare.js`, and its only non-test consumer cites its path
as a governance string without ever requiring it.

### The decision this forces, for Ben

The 19 need one of three things, and the third is a policy call:

1. **Code restructuring** so a genuine per-field evaluation site exists, for
   example explicit dispatch instead of a computed table lookup plus generic
   map and slice. Real engineering, and arguably worse code: the table-driven
   design exists to avoid a forty-branch switch.
2. For `appraisal-governed-review` only: promotion off `VALIDATED_NOT_SERVED`
   plus a real consumer. A larger lift than the other eighteen.
3. **A different verification instrument for this class of claim.**

Option 3 deserves serious consideration rather than dismissal. Ruling 5 says
"do not demote a row merely because direct-import analysis is too shallow". A
table-driven field genuinely is served when it is a member of a data structure
that is itself reachable and consumed, and when it falls within the slice the
served callers actually request. That is a rigorous, checkable proof; it is
simply a different instrument from call-graph reachability.

Such an instrument would also **correctly demote** the fields sitting beyond
index 2, which today hide inside an undifferentiated `NATIVE_UNVERIFIED`. It
would split the 17 into genuinely-served and genuinely-not-served rather than
leaving them blanket-unprovable. That is more truth, not less.

It would reduce the blocker count for any row it genuinely proves. That is
legitimate only because the proof is real. It must not be adopted for the
effect on the number, and the slice semantics must be enforced or it becomes
exactly the loosening ruling 5 forbids.

### The coupling is three-way, not two-way

Section 46 recorded two coupled defects: the bare `UNIQUE(excerpt_id)` index and
the `groupClaimsByExcerpt` read path. There is a **third**, upstream of both,
found while fixing the others.

`lib/parser-v2/store-claims.js:158` mints a claim id as
`sha256(excerptId|attribute|index)` with **no provision component**, and the
writer upserts with `{ onConflict: 'id' }` at line 269. If two sibling cards
ever share an `excerpt_id`, a claim on one sibling collides in `id` with a
same-attribute, same-index claim on the other, and the upsert **silently
overwrites one with the other at write time**. That is data loss before any
read path is involved, so none of the read-side fixes can compensate for it.

This is a live write path, in ingestion. It cannot fire today for the same
reason as the others: the DB unique index prevents two cards sharing an
excerpt.

**Consequence for the migration plan.** The index is holding two paths shut, not
one. It must not be dropped until BOTH the read-side keying (done) and
`store-claims.js` claim-id composition are corrected. Fixing `claimId` is not a
local change: adding a provision component re-mints every existing claim id, so
the next ingest would insert new rows rather than upsert existing ones and
produce duplicates. It is a data migration and belongs in the production
activation package alongside the index change, sequenced **before** it.

Ordering for the eventual package, which is now fixed:

1. read-path keying (complete);
2. `store-claims.js` claim-id composition, with a migration for existing ids;
3. only then, replace `provision_cards_excerpt_unique`.

Doing 3 before 2 converts a latent write-path defect into silent live data loss.

## 61. F5 quote fidelity: the design, before it is built

Queued behind the F3/F11 lane because it touches the same four modules.
Recording the intended approach first, because the obvious fix is wrong.

The defect: three of four bridges verify "verbatim" grounding with plain
`String.includes`. Reproduced, a fragment that drops a preceding negation is
accepted and **inverts the legal meaning**:

```text
source:   "...except as would not have a Company Material Adverse Effect..."
accepted: "have a Company Material Adverse Effect"
```

Also accepted: `"accurate"` taken from `"inaccurate"`, and arbitrary mid-quote
substrings of a Material Contracts bucket.

**Why a tighter regex is not the answer.** Word-boundary anchoring kills the
`accurate`/`inaccurate` case and the truncated-prefix case, but it does **not**
kill the negation case, which is already word-boundary aligned. Containment can
never establish semantic fidelity, because whether a sub-span preserves meaning
depends entirely on what precedes it.

**The rigorous fix is verified offsets, and the data exists for it.** The
canonical excerpt identity is already `contentId(EXCERPT_DOMAIN, { quote, start,
end })`, and the representations projection already carries `evidence.spans`.
So the check should be that the stored text equals `sourceText.slice(start,
end)`, not that the source contains it.

Intended rule, in priority order, failing closed at each step:

1. where a span offset exists, verify the stored text equals the exact slice;
2. where none exists, require exact equality with the full source quote, which
   is what `general-covenants-dark-bridge.js` already does and is the reason it
   is the only one of the four that resists this attack;
3. only if neither is possible, allow word-boundary anchored containment, and
   record that surface as weaker rather than pretending it is verified.

General Covenants is the model here, not the outlier to be relaxed toward the
others.

## 63. PLANNED, NOT BUILT: amendment handling

Ben's instruction: think it through, add it to the plan, do not build it.

### The problem

A deal's SEC filings are not one document. A later filing may be either a full
amended and restated agreement, or an amendment that modifies specific sections
of an existing one. These need different treatment and the classification is
not always obvious from the filing type alone.

### Ben's stated shape

1. If it is a **full agreement**, store it as a separate agreement.
2. If it is an **amendment**, parse what it changed against the existing
   agreement and show that in the review tab.

### Design thinking, for a later build

**Classification, and it must fail closed.** Signals include the title
("AMENDED AND RESTATED AGREEMENT AND PLAN OF MERGER" versus "AMENDMENT NO. 1
TO..."), whether a full article structure is present, document length, and
operative language such as "is hereby amended to read as follows". Getting this
wrong is expensive in both directions: treating a restatement as an amendment
loses the document's structure, and treating an amendment as a full agreement
creates a phantom agreement with almost no provisions. Ambiguous cases must go
to human review rather than being guessed.

**Full restatement path.** Store as its own agreement, linked to the
predecessor by an explicit relationship and an effective date. Extraction runs
normally. The review surface must make clear which version is being read and
offer the predecessor.

**Amendment path, the harder one.** An amendment expresses operations, not
prose. At minimum: restate a section in its entirety; delete specified words
and substitute others; insert a new subsection; delete a subsection; amend a
defined term; amend a schedule or exhibit. Parsing must capture the target
reference, the operation, and the new text, and must fail closed when the
target cannot be resolved to an existing provision unambiguously.

**Two representations will be needed, and they answer different questions.**
The delta view Ben asked for answers "what changed". A materialised effective
text answers "what does the agreement say now", which is what extraction and
cross-deal comparison need. Storing only the delta means every downstream
consumer has to recompute the effective text; storing only the effective text
loses the "as amended" trace. Expect to need both, with the delta as the
display artefact and the effective text as the extraction input.

**The legal-judgment question this forces, which is Ben's to answer.** When a
term is amended, which value is "the" value for market comparison: as signed,
or as amended? A termination fee that changed between signing and closing has
two true answers. Market statistics must pick one deliberately and label it, or
the comparison silently mixes bases. This is the same class of decision as the
derived-comparison FX and period rules, and should be recorded as a ruling.

**Interaction with work already done tonight.** Ruling 6 already requires card
identity to bind the source revision. That anticipated exactly this: an
amendment introduces a second source document for the same deal, so provisions
from the base and the amendment must be distinguishable by revision, not merely
by deal and provision. The offset-based quote verification designed in section
61 also becomes more important, because a quote must be attributed to the
correct document, and "this text appears in the source" is meaningless when
there are two sources.

**Failure mode to design against.** Silently overwriting base-agreement
provisions with amended ones. Supersession must be explicit and additive so the
original remains readable and citable.

**Test case.** Metsera is the only deal currently known to carry an amendment,
so it is the natural first fixture.

## 65. Source completeness is an admin workflow, clarified 2026-08-05

Ben clarified the shape of the corpus-completeness half of his source-trust
ruling. It is an **admin page**, not a state-machine subtlety.

> There should be an admin page where someone verifies the docs are complete.
> If they don't think they are, they can interact with an AI and say: go and
> find it.

This settles a question that was open in the state model: whether "an AI was
instructed to look for further documents" belongs in the state vocabulary. It
does not. The state is **what a human concluded**. The AI search is a tool the
human reaches for from that page when they conclude something is missing. Its
outcome is new documents, and new documents are what change the state, by
revoking a prior verification. The instruction itself is a workflow action, not
a status the corpus holds.

Keep the state vocabulary to the human conclusion: not yet verified by a human,
verified by a human, and a human has looked and believes documents are missing.

### The surface

`pages/admin/` already exists and is substantial: registry, candidates, gaps,
ingest-runs, agreements, taxonomy, review-queue, schema-loss, processing-flow,
reconciliation and reports. A source-completeness page belongs in that family
and should follow its conventions rather than inventing a new admin shell.

### What it needs to show and do

- deals, with their current human-verification status and who set it, when;
- the documents currently held for each deal, so the reviewer can see what they
  are attesting to;
- a control to mark the set complete, and one to mark it incomplete;
- from the incomplete state, the ability to instruct an AI to search for the
  missing documents.

### Two dependencies, one of them blocking

**Persistence.** Marking a corpus verified writes state. Nothing in this lane
currently writes anything, and where that state lives has not been decided. It
is not production data, but it is data, and the decision should be deliberate
rather than absorbed into a UI build.

**The AI search is extraction, and extraction is not authorised.** "Go and find
it" means retrieving further filings from EDGAR. That is precisely the capture
step that `corpus-source-discovery-capture.js` currently refuses
unconditionally, correctly, because Ben has not authorised extraction. So the
admin page is buildable up to the point of the search button, and the search
itself needs separate authority.

That split is worth taking deliberately rather than treating the page as
blocked: the verification workflow is the part that carries the judgement, and
it is independently useful even while the search is stubbed.

### Ben's sharpening, same day: the corpus state is a WARNING, not a gate

> You deem the filing verified but there is a health warning somewhere that a
> human hasn't confirmed there are no other docs etc. That lets us ingest and
> get moving. Then the human should have a page it can interact with an AI to
> figure out what the right docs are.

This is the most important constraint on the model and it must not be lost:

- **Document verification stands alone.** A filing whose text is verified is
  verified, full stop. It is not held hostage to corpus completeness.
- **The corpus state is advisory.** It renders as a health warning, visible
  wherever the data is consumed. It does **not** fence data out, block
  ingestion, or gate a route.
- **The point is to keep moving.** Ingest and work on verified filings now,
  with the open question surfaced honestly rather than blocking on it.

This is a genuinely different mechanism from the dark-authority fence, which
**rejects** records outright. That fence exists because unauthenticated data
must never be served. This warning exists because incomplete-corpus data is
perfectly good data with a caveat attached. Do not implement the second by
copying the first: a fence here would defeat the entire purpose.

Practical consequence for the state model: nothing may consume the
corpus-completeness state as an admission condition. It is display metadata. If
a future consumer wants to filter on it, that is a user choice, never a system
refusal.

### Interaction with amendments

Section 63's amendment work and this page are the same problem seen from two
ends. An amendment appearing is exactly the event that should revoke a prior
completeness verification. When amendment handling is built, it should drive
this state, not sit beside it.

`lib/query/natural-language.js` carries real hardcoded detection logic for both
kinds and needs editing rather than deletion. Saved-query storage does not
hardcode the kinds, but existing rows should be checked before engine support is
removed.

### Recommended order

1. Fix the dropped coverage footer. It is a live defect and independent of any
   of this.
2. Decide the two product questions: whether the scan matrix is wanted, and
   whether four compared deals is enough.
3. Then retire, closing the four register entries and updating the design spec

## 67. Comparison view requirements, Ben, 2026-08-05

Four decisions. The first clears the last objection to retiring
`pages/compare.js`; the other three are new requirements on the review compare
mode, which is the surface being kept.

### 1. The scan matrix is not wanted

Ben does not want the feature-by-deal summary matrix rebuilt. That was the only
genuine capability `pages/compare.js` had which review v2 lacks, so its
retirement is now clean: an orphaned, unlinked, untested 2,400-line surface
reading the raw provisions table instead of the curated cards, with a dead
cross-navigation link, and nothing worth salvaging.

### 2. Selectable terms in the comparison view

The user must be able to choose which terms appear in a comparison. Today the
review page renders all twenty configs unconditionally.

Design note: there is partial precedent in the query product's
`included_field_groups` (primary, qualifiers, mechanics, all), but that is a
coarse four-way switch over a fixed key list, not user selection. Expect this to
need two levels: which sections appear, and which rows within a section. The row
identity that `unionRows` already computes is the natural handle for the second.

### 3. No cap on compared deals, and export

`MAX_COMPARED = 3` in `components/review-v2/compareData.js` is to be removed.
Ben's stated reason matters for the design: people will want to extract to Excel
or PDF.

That reason splits the requirement in two, and they should not be conflated:

- **On screen**, N columns has real limits: N fetches of the cards endpoint
  (cached, which helps), horizontal layout, and `unionRows` cost. Large N is
  likely horizontal scroll or virtualisation rather than an unbounded table.
- **On export**, N is genuinely unbounded, because nobody is reading fifty
  columns in a browser. Export is the real consumer for large comparisons.

**Export is a new capability.** Nothing in the codebase does CSV, Excel or PDF
export today; the retirement audit confirmed `pages/compare.js` has none either.
This is a build, not a port.

### 4. Dual-scope market sidebar

When a set of deals is being compared, opening the market sidebar must show
**both**:

- the comparison across just the deals currently in the comparison set; and
- the comparison across the whole corpus, which can then be filtered.

This is the sharpest of the four requirements: "these five deals average 3.2
percent, market is 2.8 percent" is a different and often more useful question
than either alone.

Architecturally this is straightforward, which is worth recording so it is not
over-estimated. `calculateMarketStats(request, dataset, validateMetricResult)`
in `lib/row-market-stats/service.js` already takes a **dataset**. Scoping to an
arbitrary set of deals is passing a different dataset, not new statistics code.
Two invocations, two scopes, rendered as two bands in the same sidebar.

The corpus scope also needs filtering, which is closer to the screening query
kind than to anything in the review page today, and is the one part of this that
is not simply a second call.

### Sequencing note

All four land on the review compare mode, which is the surface being kept. None
of them is a new page. That is a good sign for the decision in section 64: the
retirement consolidates onto the surface that is also where every new
requirement naturally belongs.

## 37. Dark-bridge gate, 2026-08-05

`lib/canonical-v2/dark-bridge-gate.js` is built and green at 7/7. It exports
`DARK_BRIDGE_ENV_KEY`, `DARK_BRIDGE_ENABLED_VALUE`,
`isDarkBridgeIntegrationEnabled`, `assertDarkBridgeIntegrationAllowed` and
`DarkBridgeGateError`.

It is default-off. It returns true only when
`CANONICAL_V2_DARK_BRIDGE === 'ENABLED_LOCAL_PREPRODUCTION'` exactly, and then
only when none of `NODE_ENV=production`, `VERCEL_ENV=production`, `VERCEL=1` or
a truthy `CI` is present. Every missing, empty, mistyped, near-miss or
prototype-only value fails closed. It reads own properties only, so a polluted
prototype cannot enable it. It resolves its default via `arguments.length`
rather than a default parameter, so an explicit `undefined` fails closed
instead of silently falling back to the ambient `process.env`.

The gate is registered as `PURE_PROPOSAL` in
`lib/canonical-v2/phase1-authority-boundary-inventory.js`. It carries none of
the forbidden capabilities, and the authority-boundary suite is green:

```text
node --test tests/canonical-v2-phase1-authority-boundary.test.js \
  tests/canonical-v2-dark-bridge-gate.test.js
13 passed, 0 failed
```

### One deliberate deviation, flagged not silently taken

Because `VERCEL=1` is set on every Vercel runtime including preview, the gate
is currently **local-only**, not local-and-preview. That is stricter than the
instruction, which said local/pre-production. It was left strict on purpose:
loosening a safety gate while production authority is `NONE` and no reviewer is
available is the wrong direction to guess in. The consequence is that the dark
preview can only be seen by running the app locally.

To widen it to Vercel preview, the correct change is a positive allowlist
matching the existing `CANONICAL_V2_PROCESS_PILOT_UI_ENABLED` precedent
(`flag && VERCEL_ENV === 'preview'`), not deleting the `VERCEL` check. This
needs Ben's ruling first.

### The gate is not the enforced containment

is not the env var. It is the Phase-1 authority inventory plus its capability
scan, which greps every declared `PURE_PROPOSAL` source for database, network,
provider, signing, deployment, `child_process` and filesystem-write patterns
and fails the suite if any appear, together with the zero-non-test-importer
rule. The gate is a second layer for the integration seam, not the primary
containment.
